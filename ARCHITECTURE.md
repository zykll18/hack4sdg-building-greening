# Building Greening — Presentation Architecture

## Optional Zero-Carbon-Ready reference — 2026-10-17

Compare and the reader report include an optional HKGBC Zero-Carbon-Ready Building Certification reference. The January 2026 application manual, official scheme/calculator page and Energy Assessor directory are linked in the preparation checklist. This is guidance and raw annual EUI arithmetic, not an official calculator integration, rating, eligibility decision or application submission. Existing planting recommendations and report export do not depend on completing these fields.

`src/domain/zcrb-reference.js` validates assessment scope (whole building or landlord areas/services), annual electricity, matching internal floor area, data basis, source note and explicit matching-boundary/12-month confirmation. Raw EUI is annual kWh divided by internal floor area in m²; planting coverage and the multi-year greening period are never used in this arithmetic. Missing quantities, unchecked confirmation and invalid drafts cannot produce an EUI. The app does not apply official normalisation, baseline reductions or rating thresholds. Independent review of operating hours, occupancy, HVAC and exclusions remains pending even when user entries are recorded. Plant biomass and partial roof carbon results cannot establish certification.

`web/zcrb-reference.js` renders the optional form, traceable checklist and collapsed report section. Inputs are retained in the existing project snapshot as versioned, IFC-model-bound `certification` data; replacing a model clears them, restoring its complete backup restores them, and older backups remain valid. Invalid but bounded editable drafts may be saved; the report ignores invalid or differently bound certification data without blocking the planting report. User source notes are escaped. No dependencies, directories, backend endpoints, credentials, quotas, framework changes or custom error codes are introduced.

## IFC type reuse and bounded entity scope — 2026-10-16

Assistant index export no longer requests scalar attributes for every entry in the Fragments category map. It reads all display products plus explicit building/spatial categories relevant to planting (project, site, building/storey, space/zone, walls, roof/slab, coverings, openings/windows/doors, proxies and geographic elements). Non-display geometric primitives, representation records and standalone property-set entities are outside this declared query scope; associated quantities/property sets/materials remain attached to components. This is a semantic scope filter, not an arbitrary first-N cutoff. `indexScope` explains this limitation to the agent, and `excludedEntityCount` is recorded in local diagnostics. Generic full-IFC inventories are not represented as supported by this index.

The source IFC reader caches flattened, qualified property-set values by property-set GlobalId and material definition traversal by source EXPRESS identity. Common type properties are constructed once per explicit `IFCRELDEFINESBYTYPE` association, keyed by the type GlobalId; repeated `Name` strings never establish equivalence. A snapshot of direct property-set associations prevents inherited-set propagation from being mistaken for occurrence data. Occurrence values override type values by qualified property name. An explicit occurrence material association replaces the inherited material system in full, including its ambiguity flag; absent occurrence material retains the type material system. Elements with no own attributes can share the common immutable property array in the worker result. Existing elementProperties and thermal consumers still receive resolved component attributes.

`typeGlobalId` is retained in the exported/validated component identity for queries and inspection. Name, location, surface area/slope, openings and planting decisions remain per occurrence; a shared type does not imply the same suitability. Shared type/material/set counts and typed occurrence counts are included in the preparation log. The wire format still carries resolved properties per component, compressed and cached by the existing transport; it is not a new lazy attribute RPC or a fully deduplicated type dictionary on the wire. Source relationship parsing still visits the corresponding IFC relation tables once in its worker. The optimization does not promise zero parsing work or support unbounded component counts.

No dependency, directory, framework or custom error code is added. Only static review and JavaScript syntax checks were performed, respecting the user's instruction not to run tests; no browser acceptance run, live AI call, GitHub push or deployment was performed. Actual preparation-time reduction for the large building remains to be measured.


## Correlated AI run diagnostics — 2026-10-16

Each accepted frontend recommendation attempt receives a browser UUID before surface screening or IFC indexing. `X-AI-Request-Id` carries that UUID through index registration and recommendation requests; the API validates its format, falls back to a server UUID and echoes it in its response. Vercel structured logs use the same ID for HTTP outcomes, request metadata, tool start/end, sanitized argument/result summaries, model configuration, step token usage and the final validated answer. Early authorization/transport errors also produce an HTTP outcome. The separate upload operation is labelled so it is not mistaken for a second model generation. Backend timing starts at request receipt, while browser timing includes all preparation.

`web/assistant-run-log.js` retains at most 20 attempts and approximately 1 MiB of bounded diagnostics in this browser's localStorage, evicting oldest records first. Per-run events are bounded at 200 and large details are omitted/truncated explicitly. Records contain question, answer, model/provider when received, source-reported token totals, building component/index sizes, selected counts, observable stages and timings, bounded proposals/change summaries, application status, and final success/failure/timeout/cancellation. Reloaded unfinished attempts are marked interrupted. Storage failure does not block planting; persistence can be unavailable in restricted/full browsers. Unknown usage remains null, not zero, and no monetary cost is inferred. This is not cross-device storage or a complete permanent audit archive.

Project → Diagnostics exposes Download AI run logs and Clear local AI logs. Detailed traces are not shown inside Inspect. Downloads are JSON and contain user questions/replies and building labels; they are diagnostic files, not project backups. The shared `src/domain/assistant-run-log.js` sanitizer excludes credential/header fields, raw building property/index trees, audio, system prompts and internal reasoning; recognizable API-key strings are redacted. Only tool argument summaries and structural result summaries are retained, not entire IFC properties/tool results. Browser-only failures never reach Vercel, so export the local JSON to investigate pre-request failures. No dedicated logging service or new dependency is introduced, and existing project/planting schemas are unchanged. This feature covers planting chat/auto-plant runs, not audio transcription calls.

Implementation was reviewed statically and changed JavaScript files passed syntax checks. Per the user's instruction, no tests, live model requests, browser acceptance checks, GitHub push or deployment were performed.


## Large IFC query transport and preparation deadlines — 2026-10-16

IFC source relationship/property parsing now runs in a native module Web Worker (`src/adapters/ifc-query-worker.js`) so WebAssembly parsing does not block the UI timer and cancellation controls. Model reset/disposal terminates the worker; parsing has a 120-second cap. Component export checks cancellation between 100-entity batches and reports completed/total counts. The browser recommendation flow has a 180-second deadline including surface screening, component export, index upload and generation; worker promises are raced against cancellation so the panel can release even if an engine call is still pending. Existing AI generation deadlines remain 90 seconds on the server and 95 seconds in the client. Cancellation cannot instantly preempt a running engine operation; stale results are ignored.

The existing `/api/assistant` route accepts a quota-gated `X-Building-Index-Operation: register` request. It stores the complete query index separately and returns an opaque random token. Subsequent recommendations send that token plus question, selections and changing project context. A SHA-256 fingerprint detects index changes; the browser reuses its token until shortly before expiry. Missing/expired cache entries return HTTP 410 and the next user retry reuploads; there is no automatic repeated model call. Indexed properties and relationships are not silently dropped, and the complete index remains behind the existing paginated agent tools rather than being inserted into the initial model prompt.

`src/adapters/assistant-index-store.js` reuses the existing Upstash REST credentials in production. Gzip-compressed JSON is split into bounded Redis values, with a 15-minute TTL and a manifest published only after all chunks exist. Cache keys use a fixed public-demo namespace plus an unguessable token; the token is temporary cache addressing, not user identity or authentication. Raw IFC files, audio and provider keys are not stored. This adds temporary building-derived data to the existing Redis service; it is not project persistence. Development uses at most two compressed in-memory entries and does not require Redis.

Uploads retain the 4 MiB compressed request limit and allow up to 64 MiB decompressed index JSON, separate from the legacy 16 MiB request path. The full register envelope is also bounded at 64 MiB. Models exceeding these supported limits fail explicitly. Public production uploads have a separate global quota of six/minute and 100/day; generation retains the existing configured AI quota. Local development retains its shared bounded process quota. All storage fetches have a four-second timeout. No new dependency, directory, provider or framework is introduced; HTTP 410 is the standard expired-resource status, not a custom application error code.

Validation for this change is limited to static source review and JavaScript syntax checks. Per user instruction, no automated tests, browser acceptance tests, provider calls or deployment were run. Large-model upload size, worker/WASM bundling and production Redis behavior still need end-to-end verification before deployment.


## Requested biomass screening estimates for five species — 2026-10-15

Five previously qualitative species now have an explicitly curated `estimateId`, separate from their species-specific literature references and null project net-reduction factors. The shared Flora/AI carbon view computes dry biomass production × assumed carbon fraction 0.42 ×44/12; this is a potential annual biomass carbon flow, not measured ecosystem net uptake, accumulating stock, or durable project removal. It is never multiplied by project years or deducted from construction/energy totals. Failure can approach zero; the displayed positive study envelope is not a guaranteed lower bound or confidence interval.

For Arachis pintoi, the CIAT/Grof archival abstract reports the legume component of a Colombian mixed pasture yielded 5.2–9.6t DM/ha/year under four-week harvests (not total mixed-pasture yield). Converting to 0.52–0.96kg DM/m²/year gives 0.8008–1.4784kg CO₂/m²/year under the explicit 42% C assumption. This is a ground-area forage-production analogy, not a roof or planter net-carbon factor. For Ficus pumila, Trachelospermum jasminoides, Parthenocissus dalzielii and Bougainvillea spectabilis, the common climbing-facade scenario uses the five-species Berlin paper's abstract envelope 0.12–0.64kg DM/m² façade/year (doi:10.1016/j.ufug.2025.128951), giving 0.1848–0.9856kg CO₂/m²/year. These four species were not measured by that paper; their shared functional-group estimate makes no artificial species ranking. The 42% carbon assumption follows the paper's referenced carbon/DM conversion, not verified carbon fractions for these species.

Flora shows the interval, surface/area basis, formula, assumptions and sources, and AI tools carry the same explicit provenance and restrictions. Existing stock-change/flux records stay distinct. No new dependencies, framework changes, directories or backend error codes are introduced.

## Region contract and provenance

A confirmed region includes `id`, project/model version, region type, IFC GlobalId/local ID when present, display geometry source, optional edge-strip crop or ground rectangle placement, display area estimate and a separately user-confirmed `usableArea` quantity. Display geometry comes from the loaded IFC, but its area is an estimate assuming the renderer coordinate unit is metres. The proposed role and usable area require explicit confirmation. IFC categories, scalar attributes and names provide initial identity screening; this does not resolve property-set relationships or establish physical exposure. Roof candidates must have upward geometry and a compatible roof identity or upper-envelope slab, with each retained display triangle at most 20° from horizontal. Roof and terrace extraction partitions upward source faces by local slope before cropping or confirmation, recording original, eligible and excluded surface areas; a low average slope cannot admit a steep section. Terrace candidates require explicit balcony/terrace identity and each retained display triangle at most 5° from horizontal. These are configurable concept thresholds, not engineering standards. Generic floor cropping cannot create a terrace identity. Facade candidates need outward near-vertical wall geometry and are excluded when scalar attributes or names mark them internal. Geometry alone cannot detect all interiors, occlusion, services, structural capacity or openings not modeled as holes. Unknown exterior status stays conditional. Ground regions are user-defined design rectangles and are never labelled IFC boundaries or owned land.

The viewer rejects missing/current-model selection, geometry without a suitable display face, invalid dimensions, stale drafts, duplicate component assignment and overlapping ground rectangles or rectangles intersecting the conservative building bounding footprint. Confirmed usable area must fit within the selected display surface. Roof/terrace extraction keeps only locally slope-screened upward-facing triangles; facade extraction keeps outward-facing near-vertical triangles. Optional `screening.slopeScreening` metadata preserves original/eligible/excluded component areas and source slope range even when an eligible face is subsequently cropped. User-selected edge strips clip existing triangles and preserve their holes/slopes. They do not infer an approved balcony boundary.

Each overlay uses confirmed area / extracted display area × system coverage fraction. A shared clipping plane moves across the longer horizontal dimension, with its depth solved against actual clipped triangle area. This creates a continuous planted strip while preserving source openings, with surface area matching deterministic coverage. Analytical coverage uses the unmodified clipped source triangles. The display skin is offset along area-weighted normals shared by coincident vertices, so it follows curved roofs without triangle seams. The raised skin has a different physical area and is never used for coverage, costs or carbon. Plant anchors follow the raised skin while shrubs remain upright. The vegetation layer uses the same clipped triangles; area-weighted seeded sampling adds decorative plants independently of triangle count. The strip direction is a concept presentation choice, not an optimized layout. Light-touch roofs use folded low foliage and small flowers; Landscape mix roofs use raised beds and volumetric shrubs. Facades distinguish sparse climber leaf clusters/support stems from textured dense living walls. Terraces use planter boxes and shrubs; ground uses low vegetation or shrubs and small trees. A sampled footprint-clearance check avoids modeled holes and edges but is approximate, not collision or engineering validation. Decorative sizes, density and species are illustrative; counts do not enter area, cost or carbon calculations. The appearance is a concept visualization, not construction assemblies or a photoreal planting simulation. Selection uses a muted blue highlight; showing an After plan clears it to distinguish component selection from green planting. The original model object and source IFC bytes are never edited. Before hides overlays; After and plan changes rebuild them using the same region data. Model replacement/disposal clears drafts, selections, regions, GPU overlay geometries, materials and generated textures. Each plant kind is drawn with instancing and bounded density. The That Open excluded-material pass restores original planting colors after the BIM pen/ambient-occlusion passes, including technical drawing mode; disposal removes those material references before freeing resources.

## HKO climate API and IFC thermal integration — 2026-10-15

`api/climate.js` calls a fixed HTTPS HKO CLMTEMP station HKO endpoint.
